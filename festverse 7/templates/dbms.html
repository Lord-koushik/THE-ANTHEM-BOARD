Where each DBMS concept lives

ConceptIn this project
Normalisation (3NF)No repeated groups: colleges, venues, teams, coupons are separate tables referenced by key. Derived values (seats left, revenue, rank, profit) are computed in views, never stored, so they cannot go stale.
ConstraintsPK, FK with ON DELETE rules, CHECK (fee, ratings, wallet ≥ 0, end > start), UNIQUE, and a partial unique index (uq_active_registration) so cancelled rows don't block re-registering.
TriggersVenue clash, participant time clash, team size, seat limit with auto-waitlist, refund on cancel, waitlist promotion, judge conflict of interest, resource over-booking, check-in rules, audit trail. See the list below.
Stored functionsregister_for_event, cancel_registration, topup_wallet, scan_checkin, promote_waitlist, fn_recommend, fn_has_conflict.
Transactions (ACID)Registration debits the wallet, uses the coupon, inserts the row and logs the payment as one unit. If a trigger rejects it (clash, full team), everything rolls back. Each web request is a single transaction.
Concurrency controlSELECT ... FOR UPDATE on the event row serialises seat counting, so two people can't take the last seat. Waitlist promotion uses SKIP LOCKED.
Viewsv_event_stats, v_leaderboard, v_my_registrations (participant dashboard), v_fest_summary (admin), v_college_points, v_certificates, and more.
Window functions + CTEsv_leaderboard averages judges per round, sums rounds, and uses RANK() OVER (PARTITION BY event ORDER BY total, best round) for tie-breaking.
Joins and aggregatesSelf-join in fn_recommend ("people who joined X also joined Y"), FILTER aggregates, multi-way joins in analytics.
IndexingComposite and partial indexes below, plus a live before/after benchmark.
Security / RBACPostgres roles with GRANT/REVOKE (below), column-level privileges hiding password hashes, plus app-level role checks and CSRF tokens.
AuditingGeneric audit_row() trigger records old/new JSONB and the acting user (passed via set_config('app.user_id')).
